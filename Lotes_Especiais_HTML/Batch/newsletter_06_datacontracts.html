Decifrando Dados: O PagerDuty não deveria ser seu despertador (Data Contracts na Prática)

🧠 O Insight da Semana

Você acorda às 3h da manhã com um alerta do PagerDuty. O pipeline crítico da diretoria capotou. O motivo? Alguém no time de backend renomeou a coluna user_status para status_usuario no PostgreSQL de produção, e suas DAGs do Airflow travaram feio.

Isso acontece todo dia na maioria das empresas. E a nossa resposta, historicamente, tem sido encher a arquitetura de band-aids. Criamos milhares de testes do Great Expectations, do dbt, checagens de nulidade e de formato... tudo rodando depois que a ingestão acontece. Mas convenhamos: testar a estrutura do dado apenas no ambiente analítico é como verificar se os freios funcionam jogando o carro ladeira abaixo.

Precisamos tratar dados com o mesmo rigor que a engenharia de software trata APIs. Quando um dev quebra um contrato de API REST, o código não compila, a esteira barra o deploy. Por que com dados o erro só estoura no dashboard do CEO?

É por isso que a adoção de Data Contracts no modelo Shift-Left (nível de compilação) é a única saída sustentável. Significa que, se um engenheiro de software remover uma coluna transacional sem atualizar o contrato de dados, a esteira de CI/CD quebra no Pull Request dele. O erro não vira um bug de produção. O lixo nem chega no data warehouse. E, o mais importante, você volta a dormir 8 horas por noite.

📡 Radar: O Que Você Precisa Saber

  • 🛠️ A ascensão de validadores estáticos de contrato
  • O que é: O uso crescente de ferramentas open-source (como o Data Contract CLI) que checam especificações YAML de dados diretamente nos pipelines do GitHub/GitLab.

  • O Impacto: Tira a responsabilidade das falhas estruturais exclusivamente das costas da Engenharia de Dados. O contrato se torna um artefato bloqueante no deploy dos microserviços. Se o backend viola o acordo, o microserviço não sobe.

  • 🔄 Shift-Left não é tecnologia, é política

  • O que é: O movimento de puxar o controle de qualidade para o extremo esquerdo do fluxo — direto na origem, antes da emissão do dado.

  • O Impacto: O YAML é fácil. O inferno é convencer o dev transacional de que a tabela interna dele também é uma API pública para uso analítico. Implementar contratos de dados sem um patrocínio forte da diretoria vira apenas mais uma burocracia ignorada pelo time de engenharia.

  • 🔗 Schema Registry já fazia isso

  • O que é: Validar schemas de eventos (Avro/Protobuf) antes de o produtor publicar a mensagem no Apache Kafka.
  • O Impacto: Se você tem uma arquitetura orientada a eventos bem desenhada, o schema registry já age como um Data Contract de compilação. Se o payload não respeitar o schema, o broker simplesmente rejeita a mensagem. Ponto para o streaming.

🛠️ Mão na Massa (Pragmatismo)

Quer validar um contrato de dados amanhã sem pedir orçamento para comprar ferramentas SaaS gigantescas? Comece simples.

Não mude a arquitetura inteira. Crie um arquivo vendas_data_contract.json (usando JSON Schema) no repositório do backend. Especifique as colunas intocáveis e seus tipos (ex: user_id, amount, currency).

Adicione um step rápido no GitHub Actions do time de software. Use uma ferramenta leve como o ajv-cli (validador de JSON) ou escreva um script Python de 20 linhas que bate o DDL das migrações do banco (como o Alembic ou Flyway) contra o seu JSON.

Se a migração do PR renomeia o user_id e quebra o contrato, a action fica vermelha. Você acaba de implementar a fundação do shift-left.
