Decifrando Dados

🧠 O Insight da Semana

Existe uma epidemia silenciosa nas equipes de dados: a fobia de SQL.

Você já viu o roteiro. Um processo batch precisa agrupar vendas por região e filtrar as devoluções. Uma query de 15 linhas resolveria isso em segundos no BigQuery ou Snowflake. Mas alguém no time decide que isso "precisa escalar". De repente, nasce um script em PySpark com 300 linhas, dezenas de dependências e um pipeline de CI/CD inteiro só para fazer um simples GROUP BY.

Isso não é engenharia de software aplicada a dados. É puro ego.

Nós, engenheiros, adoramos a complexidade. Achamos que se a solução não envolver um cluster distribuído ou um DataFrame cheio de lambdas, nosso trabalho não tem valor. A dura realidade? Seu cluster Spark gastando centenas de dólares para processar 500MB de dados é um atestado de incompetência arquitetural. O melhor engenheiro de dados não é aquele que escreve o código Python mais abstrato. É aquele que resolve o problema do negócio com a ferramenta mais simples e barata possível. E, na esmagadora maioria das vezes, essa ferramenta já foi inventada nos anos 70.

📡 Radar: O Que Você Precisa Saber

  • 🦆 DuckDB engolindo o processamento local
  • O que é: O DuckDB continua devorando casos de uso onde antes o Pandas reinava sozinho na máquina local.

  • O Impacto: Se você ainda puxa dados inteiros para a RAM só para filtrar e agregar no seu notebook, está perdendo tempo. O DuckDB roda SQL analítico direto em arquivos Parquet ou CSV com uma performance absurda, sem precisar de um cluster. Simplicidade vencendo a força bruta.

  • 🦀 Polars estabilizando sua API

  • O que é: A biblioteca de processamento de dados em Rust atingiu um nível de maturidade que a coloca como substituta real e de altíssima performance para o Pandas.

  • O Impacto: Quando você realmente precisa escrever código (e o banco de dados não dá conta), o Polars te obriga a pensar em expressões em vez de loops preguiçosos. É a ponte ideal entre a mentalidade declarativa do SQL e a flexibilidade pesada do Python.

  • ⚙️ O pêndulo do Modern Data Stack voltando

  • O que é: Empresas estão começando a abandonar a fragmentação extrema (uma ferramenta para ingestão, outra para transformação, outra para reverso...) em favor de arquiteturas mais enxutas.
  • O Impacto: Manter 15 SaaS diferentes colados com fita crepe e DAGs no Airflow não é "moderno", é um pesadelo operacional. A engenharia está percebendo que a complexidade do stack terceirizado virou o maior gargalo de manutenção.

🛠️ Mão na Massa (Pragmatismo)

Antes de abrir um Jupyter Notebook ou criar um job no Glue/Dataproc, faça o "Teste da Janela":

Se a sua transformação de dados cabe em uma Window Function do SQL (ROW_NUMBER(), LEAD(), LAG(), SUM() OVER()), ela DEVE ser feita em SQL no próprio motor do banco.

Exemplo prático: Calcular a diferença de vendas entre hoje e ontem. Em Python, você precisa ordenar, aplicar um shift(), alinhar índices e rezar para os NaNs não quebrarem o pipeline lá na frente.

Em SQL: sql SELECT data_venda, valor, valor - LAG(valor) OVER(ORDER BY data_venda) AS diferenca_dia_anterior FROM vendas; Zero dependências de memória da sua máquina. Zero gargalo de rede trafegando gigabytes para o seu script. Tudo processado no motor hiper-otimizado do seu Data Warehouse. Deixe o Python para orquestração, integrações complexas de API e machine learning. O trabalho braçal e aritmético de conjuntos? Devolva para o banco.
